# Language Theory

Language theory studies how source code is structured (tokenization, parsing) and how its meaning is checked (type systems). It is relevant whenever a language must be designed, implemented, or extended.

> **Authoritative sources**
> - [Compilers: Principles, Techniques, and Practice (Aho, Lam, Sethi, Ullman)](https://cs.stanford.edu/people/ouster/compilers-book.html)
> - [Types and Programming Languages (Pierce)](https://www.cis.upenn.edu/~bcpierce/tpl/)

## Formal grammars and the Chomsky hierarchy

A **formal grammar** $`G = (V, \Sigma, R, S)` is a tuple of:
- $`V`: a finite set of **non-terminals** (symbols that can be expanded),
- $`\Sigma`: a finite set of **terminals** (symbols that appear in the final string),
- $`R`: a set of **production rules** $`A \to \alpha` (replace non-terminal $`A` with string $`\alpha`),
- $`S \in V`: the **start symbol**.

The **Chomsky hierarchy** classifies grammars by the restrictiveness of their production rules:

<table>
<tr><th>Class</th><th>Production form</th><th>Automaton</th><th>Example</th></tr>
<tr><td>Regular (Type-3)</td><td><i>A</i> → <i>a</i> | <i>aB</i> (right-linear)</td><td>DFA / NFA</td><td>Tokenizers, regex</td></tr>
<tr><td>Context-free (Type-2)</td><td><i>A</i> → <i>α</i> (<i>α</i> ∈ (<i>V</i> ∪ <i>Σ</i>)*)</td><td>Pushdown automaton</td><td>Arithmetic, statements, expressions</td></tr>
<tr><td>Context-sensitive (Type-1)</td><td><i>αAβ</i> → <i>αγβ</i>, |<i>γ</i>| ≥ 1</td><td>Linear-bounded automaton</td><td>Some natural-language fragments</td></tr>
<tr><td>Unrestricted (Type-0)</td><td><i>α</i> → <i>β</i> (any form)</td><td>Turing machine</td><td>General computation</td></tr>
</table>

Programming languages are almost entirely **context-free**: their syntax (expressions, statements, declarations) is generated by context-free grammars. Tokenization is a **regular** problem. The boundary between the two is what separates the lexer from the parser.

<details><summary>Details</summary>

**Why the hierarchy matters for compilers**: a regular grammar can be recognized by a finite-state machine (no memory beyond the current state), which is exactly what a tokenizer does. A context-free grammar requires a stack (unbounded memory), which is what a parser uses. This is why tokenization is "easier" than parsing: it needs less memory and simpler logic.

**Example grammar** (arithmetic):
```
E → E + T | T
T → T * F | F
F → ( E ) | id
```
Here $`V = \{E, T, F\}`, $`\Sigma = \{+, *, (, ), id\}`, $`S = E`. The grammar is context-free because every production has a single non-terminal on the left.

The broader decidability and complexity questions ("can we always decide if a string is in the language?", "how fast?") are studied in [Theory of Computation](../Algorithmics/Theory-of-Computation.md).

</details>

## Automata

Each grammar class in the Chomsky hierarchy corresponds to a class of **automata** (abstract machines that recognize the language):

<table>
<tr><th>Grammar class</th><th>Automaton</th><th>Memory</th><th>Parser strategy</th></tr>
<tr><td>Regular</td><td>DFA / NFA</td><td>None (state only)</td><td>Table-driven lexer (flex, lex)</td></tr>
<tr><td>Context-free</td><td>Pushdown automaton (PDA)</td><td>Stack</td><td>LL (top-down), LR (bottom-up), PEG</td></tr>
<tr><td>Context-sensitive</td><td>Linear-bounded automaton</td><td>Tape bounded by input</td><td>General backtracking</td></tr>
<tr><td>Unrestricted</td><td>Turing machine</td><td>Unbounded tape</td><td>Undecidable in general</td></tr>
</table>

<details><summary>Details</summary>

**DFA (Deterministic Finite Automaton)**: a set of states, a transition function $`\delta: Q \times \Sigma \to Q`, one start state, and a set of accept states. At each step, exactly one transition is possible. Tokenizers are DFAs: the current state encodes "I am inside a number", "I am inside a string literal", etc.

**NFA (Nondeterministic Finite Automaton)**: allows multiple transitions from a state on the same symbol (or $`\epsilon`-transitions). NFAs are equivalent in power to DFAs but can be more compact. Tools like `flex` build an NFA from regexes, then determinize it into a DFA.

**Pushdown Automaton (PDA)**: a finite automaton augmented with a stack. The stack allows it to match nested structures (parentheses, blocks). This is the theoretical model behind all context-free parsers. In practice, parsers do not run a PDA directly; they use table-driven algorithms (LL, LR) or recursive descent that simulate the PDA's stack with the call stack or an explicit stack.

The mapping grammar class → automaton → parser strategy gives a unifying framework: the more memory the automaton needs, the more complex the parser algorithm.

</details>

## Tokenizers

A **tokenizer** (lexer) converts a character stream into a sequence of **tokens**: keywords (`if`, `let`), literals (`42`, `"hello"`), operators (`+`, `=>`), identifiers, and punctuation. It is implemented as a **DFA** (a regular-language recognizer).

<details><summary>Details</summary>

**Lexical analysis** is a regular language problem: the set of valid tokens is described by regular expressions. Tools like `lex`/`flex` generate C code from regex specifications. The DFA states track what kind of token is being read (number, identifier, string, comment, etc.).

**Maximal munch**: the tokenizer always takes the longest possible match. `a++` → `a`, `++` (not `a+`, `+`). `a->b` → `a`, `->`, `b` (not `a-`, `>b`).

**Preprocessing**: many languages (C, C++) have a preprocessor that handles `#include`, `#define`, and conditional compilation before tokenization.

**Why tokenization is separate from parsing**: the regular-language restriction means the lexer can be a simple, fast table-driven loop with no backtracking. The parser then works on a clean token stream, free from character-level concerns. This separation is a direct consequence of the Chomsky hierarchy: regular ⊂ context-free.

</details>

## Parsers

A **parser** converts a token sequence into an **AST** (Abstract Syntax Tree) using a **context-free grammar**. The main strategies are:

<table>
<tr><th>Strategy</th><th>Direction</th><th>Grammar class</th><th>Lookahead</th><th>Notes</th></tr>
<tr><td>Recursive descent</td><td>Top-down</td><td>LL(1) (no left recursion)</td><td>1 token</td><td>Hand-written; one function per rule</td></tr>
<tr><td>LL(k)</td><td>Top-down</td><td>LL(k)</td><td><i>k</i> tokens</td><td>Table-driven; generated by tools (ANTLR)</td></tr>
<tr><td>LR(k)</td><td>Bottom-up</td><td>LR(k)</td><td><i>k</i> tokens</td><td>Table-driven; shift-reduce; handles left recursion</td></tr>
<tr><td>PEG</td><td>Top-down</td><td>PEG (ordered choice)</td><td>1 token (backtracking)</td><td>Unambiguous by construction; left recursion must be eliminated</td></tr>
</table>

Parsing is the second stage of the [Compilation](./Compilation.md) pipeline, after tokenization and before semantic analysis.

<details><summary>Details</summary>

**Recursive descent**: hand-written top-down parser; one function per grammar rule. Simple, debuggable, but limited to LL(1) grammars (no left recursion). Used in many language implementations (e.g., Go's compiler, Python's `ast` module).

**Shift-reduce** (LR): maintain a stack of tokens and states. **Shift**: push the next token. **Reduce**: replace the top of the stack with a non-terminal when it matches a production. The **conflict** (shift-reduce, reduce-reduce) determines whether a grammar is LR(1). LR parsers handle left-recursive grammars naturally, which is why they are the workhorse of C/C++/Java compilers.

**PEG** (Parsing Expression Grammar): uses **ordered choice** ($`e_1 / e_2` tries $`e_1` first, falls back to $`e_2` only if $`e_1` fails). This makes PEGs **unambiguous by construction** (the first successful alternative wins). However, PEGs do **not** always terminate: left-recursive rules (e.g., `expr: expr '+' term`) cause infinite recursion and must be rewritten (e.g., `expr: term ('+' term)*`). PEG parsers are used in the `peg` crate (formerly `rust-peg`) for Rust, in PEP 617 (the PEG-based parser in CPython 3.9+), and in the `parsimonious` third-party library for Python.

## Language design properties

Beyond parsing, language theory addresses properties that shape how a language feels to use and extend.

<details><summary>Details</summary>

**REPL** (Read-Eval-Print Loop): an interactive environment that reads an expression, evaluates it, prints the result, and loops. It requires an evaluator that maintains a persistent environment across expressions (variables defined in one expression are visible in the next). Languages with a REPL (Lisp, Scheme, Python, Ruby, Elixir) are well-suited to exploratory programming and teaching.

**Homoiconicity**: the language's data structures (e.g., Lisp s-expressions) are the same as its code. `(+ 1 2)` is both a list and a program. This enables **macros** (code that manipulates code at compile time), because the macro system can read and rewrite the program's own data structures. Most mainstream languages (C, Java, Python) are not homoiconic; their syntax is not directly representable as a data structure.

These properties interact with [Control Flow and Semantics](./Control-Flow-and-Semantics.md): a REPL's persistent environment is essentially a long-lived scope, and homoiconicity affects how control-flow constructs can be extended via macros.

</details>

## Type theory

A **type system** assigns types to expressions and checks that operations are valid. **Static types** are checked at compile time; **dynamic types** at runtime.

<details><summary>Details</summary>

**Structure**:
- **Product types** (tuples, structs): $`A \times B`. **AoS** (Array of Structs): `[{x, y}, {x, y}, ...]`. **SoA** (Struct of Arrays): `[{x, x, ...}, {y, y, ...}]`. SoA is cache-friendly for SIMD.
- **Sum types** (enums, tagged unions): $`A + B`. Exhaustive pattern matching.
- **Function types**: $`A \to B`.

**Functionality**:
- **Duck typing**: "if it quacks like a duck..." (Python, JavaScript). No static check; errors at runtime.
- **Strong vs. weak typing**: strong types do not allow implicit conversions (Rust, Haskell); weak types do (JavaScript: `"1" + 1 = "11"`).
- **Nominal vs. structural**: nominal types are distinct by name (`struct Point1 {x, y}` ≠ `struct Point2 {x, y}`); structural types are compatible if their shapes match (TypeScript, Go interfaces).
- **Hindley–Milner type inference**: infer types from usage without annotations. $`f x = x + 1` infers $`f: \text{Num} a \Rightarrow a \to a`.
- **Polymorphism**: parametric (generics: $`\forall a. [a] \to [a]`) and ad hoc (overloading: `+` for `Int` and `Float`).
- **Subtyping**: $`A \leq B` means values of $`A` can be used where $`B` is expected. **Contravariance**: function parameters are contravariant ($`(A \to C) \leq (B \to C)` if $`B \leq A`).

Type checking is the semantic-analysis phase in the [Compilation](./Compilation.md) pipeline, and the types it assigns determine the semantics of [Control Flow and Semantics](./Control-Flow-and-Semantics.md) (e.g., what a `match` must cover).

</details>

## Example problem

**Problem**: Given the grammar $`E \to E + T \mid T,\; T \to T * F \mid F,\; F \to (E) \mid id`, parse the expression `a + b * c` and show the AST.

<details><summary>Solution</summary>

This is an LR(1) grammar (standard arithmetic with precedence: `*` binds tighter than `+`).

**Parse** (shift-reduce):
1. Shift `a` → stack: `a`
2. Reduce `a → F` → stack: `F`
3. Reduce `F → T` → stack: `T`
4. Reduce `T → E` → stack: `E`
5. Shift `+` → stack: `E +`
6. Shift `b` → stack: `E + b`
7. Reduce `b → F → T` → stack: `E + T`
8. Shift `*` → stack: `E + T *`
9. Shift `c` → stack: `E + T * c`
10. Reduce `c → F` → stack: `E + T * F`
11. Reduce `T * F → T` → stack: `E + T`
12. Reduce `E + T → E` → stack: `E` ✓

**AST**:
```
    +
   / \
  a   *
     / \
    b   c
```

The `*` is a child of `+`, not a sibling, reflecting that `b * c` is evaluated first.

</details>
